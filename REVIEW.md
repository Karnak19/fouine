# Review guidance

- For remote lookups that determine a write or checkout target, treat errors and unknown states as failures. Do not convert lookup failures into “not found” and proceed with a default branch or potentially stale content; fail closed and preserve retry behavior so existing data is not overwritten or lost.
- When a finding depends on code apparently missing from the changed branch, verify the current target branch and the eventual merge base before concluding that integration is absent. A stale PR base can omit an already-landed dependency and produce a false positive; distinguish stale-base findings from defects in the PR itself.
- Review the final patch and current file state, not an earlier version, commit, title, or description from a PR whose intent changed during development; re-check a suspected defect against the latest diff before reporting it.
- Treat numeric configuration from environment variables as untrusted input. Reject blank, non-finite, non-positive, and otherwise invalid values before they can disable a safety ceiling or watchdog; use a safe default or fail startup, and test the malformed-value cases through the observable behavior.
- Keep tests hermetic: do not invoke real registries or external services when a local deterministic fixture can exercise the same failure path. For timeout/abort tests, use an injected deadline that is shorter than the deterministic operation being tested so the intended branch cannot silently stop being covered.
- For related aggregates, apply population and time filters using the same canonical parent event and scope as the other panels. Asynchronously created child rows must not determine whether an in-range parent is included; add regression coverage for child records created both inside and outside the selected window.
- Treat concurrency-scoped names and mutable state as per-run data. Audit temporary refs, files, environment, and fetch destinations for collisions between simultaneous reviews—even when operations succeed—then resolve or capture identifiers before later work can observe another run’s state.
- When a deferred action (auto-retry timer, delayed follow-up) must stand down once superseded, check its guard against durable state, not only in-memory “currently running” bookkeeping that is cleaned up on completion. Enumerate the interleavings — a newer run that completed, failed, or was manually triggered during the delay owns the resource exactly as much as a running one — and prefer the fix that deletes the duplicate in-memory check in favor of the authoritative record.
- When behavior depends on tool-specific pattern or exclusion semantics, do not infer it from a similar tool such as Git; verify the actual tool’s documented semantics or a minimal build/runtime fixture before reporting a blocking defect. For build/bundler defects, the fixture that isolates the failing layer (plugin, bundler hook, module graph) is the core of the finding — present specific remedies as hypotheses to try, and confirm a suggested lever actually works (e.g. by enabling it) before prescribing it as the fix.
- Preserve trust boundaries for grounded features: do not accept client-supplied assistant prose or tool results as authoritative. Normalize history to user input or server-owned state, and validate/cap request content before parsing, normalization, or provider work.
- Review resource limits across the whole lifecycle, not only at the final response. Row/value caps applied after unbounded query execution or materialization do not provide a real safety bound; bound work with an interruptible deadline and bound data as it is produced where the runtime permits.
- When a row cap can cut a logical multi-row group at the boundary, do not render the partial group as complete. Apply the rule to the returned data rather than a nominal output type, retain only complete groups when possible, report truncation, and test a cap landing inside a group.
- When summarizing multiple sources, attach missing-detail or unexplained-result notices to the individual source that lacks detail. Output from one source must not suppress a diagnostic for a failed source whose only evidence is logs or whose annotations are absent.
- For a user-facing rename, update the complete presentation surface—labels, empty states, and relevant documentation—not only the implementation. Preserve intentional compatibility aliases and internal paths/routes/identifiers when they are explicitly part of the transition rather than treating every textual occurrence as stale.
- When a shared helper already exists for the same operation, consolidate new call sites onto it instead of introducing a private duplicate; duplicated infrastructure helpers can drift in behavior and error handling. Either consolidation direction resolves it — unifying a stray inline site onto the helper is as valid as deleting the duplicate — and a helper whose body documents tested-and-rejected alternatives is recorded knowledge, not bloat to delete for a shorter diff.
- When a migration drops a visual or interaction state (focus ring, hover, motion), the fix must restore the whole declaration cluster the state needs to actually render — positioning and stacking context, not just the visible stroke — and any behavior delta versus the old implementation (e.g. keyboard-only vs click focus) must be surfaced as an intentional change, not passed off as a byte-for-byte port.
- Treat visual-diff evidence with the same skepticism as code evidence: asynchronously rendered UI (install prompts, mid-pulse badges) yields huge spurious diffs if captured too early, and browser automation can reattach to the wrong tab entirely. Confirm a screenshot shows the target app in a deterministic state before attributing pixel differences to the PR.
- When a rule or policy is deliberately moved to a new single home (system prompt, shared config), grep the repo for surviving copies of the old wording. Tool descriptions and other text injected into the model’s context are the dangerous copies — a stale duplicate contradicts the new rule at the exact decision point and silently reinstates the removed behavior.
- Respect documented override boundaries in prompt/configuration files. Do not report a rule's placement in an intentionally overridable default as a defect merely because a fixed system prompt could enforce it, unless the resulting behavior is demonstrably unsafe or contradicts the stated contract.
