# Review guidance

- For remote lookups that determine a write or checkout target, treat errors and unknown states as failures. Do not convert lookup failures into “not found” and proceed with a default branch or potentially stale content; fail closed and preserve retry behavior so existing data is not overwritten or lost.
- When a finding depends on code apparently missing from the changed branch, verify the current target branch and the eventual merge base before concluding that integration is absent. A stale PR base can omit an already-landed dependency and produce a false positive; distinguish stale-base findings from defects in the PR itself.
- Review the final patch and current file state, not an earlier version, commit, title, or description from a PR whose intent changed during development; re-check a suspected defect against the latest diff before reporting it.
- Treat numeric configuration from environment variables as untrusted input. Reject blank, non-finite, non-positive, and otherwise invalid values before they can disable a safety ceiling or watchdog; use a safe default or fail startup, and test the malformed-value cases through the observable behavior.
- Keep tests hermetic: do not invoke real registries or external services when a local deterministic fixture can exercise the same failure path. For timeout/abort tests, use an injected deadline that is shorter than the deterministic operation being tested so the intended branch cannot silently stop being covered.
- For related aggregates, apply population and time filters using the same canonical parent event and scope as the other panels. Asynchronously created child rows must not determine whether an in-range parent is included; add regression coverage for child records created both inside and outside the selected window.
- Treat concurrency-scoped names and mutable state as per-run data. Audit temporary refs, files, environment, and fetch destinations for collisions between simultaneous reviews—even when operations succeed—then resolve or capture identifiers before later work can observe another run’s state.
- When a deferred action (auto-retry timer, delayed follow-up) must stand down once superseded, check its guard against durable state, not only in-memory “currently running” bookkeeping that is cleaned up on completion. Enumerate the interleavings — a newer run that completed, failed, or was manually triggered during the delay owns the resource exactly as much as a running one — and prefer the fix that deletes the duplicate in-memory check in favor of the authoritative record.
- Treat teardown as preventing future work, not only stopping in-flight work. An interrupt cannot stop a prompt that has not been issued yet, and a release that early-returns on a missing handle cannot cover a late-arriving setup result; guard late arrivals (released flag checked when setup resolves) and check torn-down before every post-teardown action, with the check and the action in one synchronous block so no window sits between them.
- When behavior depends on tool-specific pattern or exclusion semantics, do not infer it from a similar tool such as Git; verify the actual tool’s documented semantics or a minimal build/runtime fixture before reporting a blocking defect. For build/bundler defects, the fixture that isolates the failing layer (plugin, bundler hook, module graph) is the core of the finding — present specific remedies as hypotheses to try, and confirm a suggested lever actually works before prescribing it as the fix: enable it, or for state-timing remedies trace whether the updated value is visible where the fix reads it (a same-tick setState is not). Verify claimed library defaults against the installed version before calling a flag dead config. For structured-output model calls, verify in the installed provider dist whether the schema reaches the wire or degrades to bare json_object, and require the prompt to state the exact JSON shape so a client-side-only schema cannot silently turn the feature into fail-closed on every call.
- Preserve trust boundaries for grounded features: do not accept client-supplied assistant prose or tool results as authoritative. Normalize history to user input or server-owned state, and validate/cap request content before parsing, normalization, or provider work.
- When sanitizing untrusted model output, audit every structural field the renderer walks, not only the field the filter was written for. A pass-through on a sibling field recreates the exact hole the filter closes; a sanitized element should carry only the fields the allowlist names.
- In multi-step model pipelines, state a producer convention where the producer reads, not only where the consumer reads. A rule visible only to the layout step cannot fix SQL the data step writes; state the convention symmetrically on both sides the way the schema doc is stated.
- Review resource limits across the whole lifecycle, not only at the final response. Row/value caps applied after unbounded query execution or materialization do not provide a real safety bound; bound work with an interruptible deadline and bound data as it is produced where the runtime permits.
- When a row cap can cut a logical multi-row group at the boundary, do not render the partial group as complete. Apply the rule to the returned data rather than a nominal output type, retain only complete groups when possible, report truncation, and test a cap landing inside a group. When the axis comes from a shared spec with several consumers of one key, resolve it from a consumer that names the axis — a table/tile view listed first carries none and silently restores the row-cut path.
- When summarizing multiple sources, attach missing-detail or unexplained-result notices to the individual source that lacks detail. Output from one source must not suppress a diagnostic for a failed source whose only evidence is logs or whose annotations are absent.
- For a user-facing rename, update the complete presentation surface—labels, empty states, and relevant documentation—not only the implementation. Preserve intentional compatibility aliases and internal paths/routes/identifiers when they are explicitly part of the transition rather than treating every textual occurrence as stale.
- When a shared helper already exists for the same operation, consolidate new call sites onto it instead of introducing a private duplicate; duplicated infrastructure helpers can drift in behavior and error handling. Either consolidation direction resolves it — unifying a stray inline site onto the helper is as valid as deleting the duplicate — and a helper whose body documents tested-and-rejected alternatives is recorded knowledge, not bloat to delete for a shorter diff. Prefer server-derived types over hand-copied unions when the typed client already carries the server schema; a second list with zero writers is drift without function.
- When a finding rests on a negative claim — an export is unused, a shape was never duplicated, nothing emits a class — ground it in a sweep of the whole repo, not only the directories the diff touches, and state the scope you searched. A too-narrow grep yields a premise that is half wrong, and the wrong half can invert the remedy: deleting an “unused” abstraction that is in fact a cross-file duplicate keeps the duplication it exists to remove. Follow export * chains in the installed package to the value export before calling something unavailable, verify a single module instance before prescribing instanceof over duck-typing, and require tests to construct the real class so a duplicated module graph fails loudly instead of silently disabling the branch.
- When a migration drops a visual or interaction state (focus ring, hover, motion), the fix must restore the whole declaration cluster the state needs to actually render — positioning and stacking context, not just the visible stroke — and any behavior delta versus the old implementation (e.g. keyboard-only vs click focus) must be surfaced as an intentional change, not passed off as a byte-for-byte port.
- For large behavior-preserving migrations, certifying parity is only half the review — weigh the churn itself. When the same facts cost substantially more source lines to read and maintain forever (formatting expansion, one declaration per line), surface that arithmetic early; a fully verified migration can still be rightly rejected on cost alone.
- Treat visual-diff evidence with the same skepticism as code evidence: asynchronously rendered UI (install prompts, mid-pulse badges) yields huge spurious diffs if captured too early, and browser automation can reattach to the wrong tab entirely. Confirm a screenshot shows the target app in a deterministic state before attributing pixel differences to the PR. Parity claims are bounded by their coverage: probe the whole page rather than a subtree, include the routes that exercise distinct dependency trees, and make the harness assert what it is measuring (explicit route, private session) — an unmeasured route can be wholly broken while every measured one matches.
- When a rule or policy is deliberately moved to a new single home (system prompt, shared config), grep the repo for surviving copies of the old wording. Tool descriptions and other text injected into the model’s context are the dangerous copies — a stale duplicate contradicts the new rule at the exact decision point and silently reinstates the removed behavior. When flipping a global default, apply the same sweep to per-site overrides that preserve the old behavior — especially on the page where the symptom bites hardest.
- Respect documented override boundaries in prompt/configuration files. Do not report a rule's placement in an intentionally overridable default as a defect merely because a fixed system prompt could enforce it, unless the resulting behavior is demonstrably unsafe or contradicts the stated contract.
- When a confirm guards an arming or destructive save, fail closed on unresolved data: an inherit/default selection whose backing settings have not loaded must take the dangerous branch and require confirmation, not compute effective-off and skip the dialog.
- Register pipeline runs synchronously before the first network call (insert row + onStart first) so supersession and stop cover the fetch window; move fallible fetches inside the guarded run so the onExit finaliser marks failures instead of stranding pending rows.
- When a new trigger or row type breaks an existing data invariant (e.g. pr_number > 0 no longer means a PR), audit every consumer of that invariant — chat prompt docs, dashboard groupings and insights, reviewed-since filters — not just the pipeline itself.
- For bot-authored PR merge gates, human approval means a non-bot login on the armed SHA: exclude all *bot logins (not just the app's own) and filter reviews to commit_id === armed SHA, or another bot's approval or a stale-SHA approval merges unreviewed code.
- Scope destructive cleanup to the snapshot evaluated (e.g. DELETE … WHERE sha = evaluated SHA); keep unconditional deletes only where the event is authoritative (push/close). Wrap webhook command paths fail-soft with try/catch + log — an unguarded throw becomes a 500 with days of redeliveries.
- Timeout every GitHub boundary including client and token creation (catchAll catches errors, not hangs); never await sweeps at boot — fire-and-forget with the interval as the retry so a degraded GitHub cannot hold the port closed.
- When documenting per-field keep/delete/no-op semantics, state the rule once rather than enumerating field groups or counts; enumerated groups drift and turn a later semantic change into a client-visible data-loss instruction.
- When indexing a fixed lookup table by request-supplied input (route params, query strings), guard with `Object.hasOwn`, not `in` or a truthiness check. Prototype names (`constructor`, `toString`, `__proto__`) walk `Object.prototype`, bypass the invalid-input branch, and execute the wrong path with valid-looking data; grep for the established guard pattern in the same file before accepting a new dynamic lookup.
- When empty-string settings mean unset, use the same falsy semantics (`||`, never `??`) in every resolution and reporting path. A split lets status and behavior diverge — one surface reports a fallback source while the other acts on the empty value — so audit new key/config slots for matching operators on both sides.
